# RL Tracker — v1 roadmap

**Source spec**: `2026-10-15-rl-tracker-features-map.md` (the map). Each work package (WP) cites
the map sections it implements. This roadmap sets the build order, scope, dependencies, open
decisions, test seams and done-criteria. It does not design the WPs internally.

## How to use it
- Do one WP at a time, in order.
- Each WP starts in plan mode (`design-before-building`, TDD, review passes). Its plan is saved as
  `docs/plans/YYYY-MM-DD-wpN-<slug>.md`.
- Keep the status line under each WP current: todo / in progress / done, with the date and a link
  to its plan.
- Any WP whose own plan exceeds one session splits again (a/b) before building.

## Cross-cutting rules
Every WP inherits these; they aren't repeated below.
- **Runtime**: Bun (runtime, package manager, `bun:sqlite`). The map's `npm install` / `npm run …`
  names read as `bun install` / `bun run …` (see "Runtime revisited" under the map's "Stack").
- **Code quality**: strict TypeScript and `typescript-eslint` strict from day one.
- **Tests**: Vitest for pure logic; a Playwright smoke check for each page.
- **Logging**: the structured logger (WP1) at external calls and decision points.
- **Little or no data** (map): no fake zeros. Hide empty items. A page that can't say anything
  yet shows a page-level "not enough data yet" note.
- **Local only**: the server binds `127.0.0.1` only, and data stays local.
- **UI work**: UI WPs load `ui-implementation-guidelines`; chart WPs also load `dataviz`. The visual
  reference is the `prototype/*` branches named in the map.
- **UI interaction defaults** (set after WP6a-a's review, where every long loop ended by
  simplifying the design). A WP that departs from one says why in its plan:
  - Focus: one rule, WP6a-a's. Focus moves to the page's main control only when a load dropped
    it to the page, to the control that changed after a change (not on Back/Forward), and
    otherwise stays put.
  - Loading: no placeholder data. The loading area shows a loading state; controls never act on
    the previous page's data.
  - Native controls (`<select>`, `<details>`, the `popover` attribute, `<dialog>`, links) before
    hand-built menus or popovers.
  - Charts stay passive: SVG `<title>` or a visible table for values, click-throughs as real
    links, no custom keyboard navigation between points.
  - Undo shows inline beside the change, not as a toast.
  - Cache: refetch everything a live event could touch; narrow it only for a measured cost.
- **Match records only**: pages read match records, never `raw.db`. Anything a page shows is
  computed at match end (map, "Raw event storage").
- **Private matches** (playlist 6) are left out of overall stats and the 30-day average by default.
  This lives in the shared filter logic (WP5a), not in Friends.
- **Dev tooling stays out of the app**: the rule registry's doc, `rules-diff`, the rule corpus and
  evidence reports are for us as developers (scripts and tests). The end user only installs,
  updates and sees stats; after an update, whether to recompute past matches is their choice.

## Test fixtures
- `captures/` is gitignored and holds other players' names and IDs.
- WP3a commits small anonymised excerpts to `test/fixtures/`, with stable fake `PrimaryId`s and
  names.
- Those excerpts are the seam for WP3–WP4 and the seed data for UI tests.

## WP2: Storage
Status: done (2026-10-16, `docs/plans/2026-10-16-wp2-storage.md`; ADR
`docs/decisions/2026-10-16-bun-runtime.md`). Notes for later WPs:
- `scheduleMaintenance` (`src/server/maintenance.ts`: retention + hourly daily-backup check)
  exists but isn't started: WP3b wires it into the long-running process, passes the recorder's
  `isRecording`, and awaits its `stop()` before closing storage.
- The `settings` table has no keys or Zod schema yet: WP8 defines both (and `src/shared/schemas`).
- Task Scheduler doesn't restart a task that crashes after launching (tested): WP3b designs its
  own restart.
- **Map**: Data location, reinstall and backup; Raw event storage; Retention timing; Periods
  (seasons seed); Identifying you (ID list).
- **Depends on**: WP1.
- **Decision — Bun-on-Windows check** (`research` first, then a spike; ADR in `docs/decisions/`
  recording the runtime switch):
  - `bun:sqlite`'s bundled SQLite version (`VACUUM INTO` needs 3.27 or later), the `auto_vacuum`
    and `incremental_vacuum` pragmas, and transactions.
  - Whether Vitest runs under Bun, and whether Playwright's runner needs Node. If either fails,
    fall back to `bun test` for logic, or to Node only for Playwright.
  - Whether a long-running `bun.exe` started from Task Scheduler restarts on crash and writes logs
    cleanly.
  - Exit: if Bun fails a must-have, raise it with the user before building on it. Don't switch
    back silently.
- **Scope**:
  - DB access behind one thin module (open, migrate, query helpers), so the driver can be swapped.
  - Open `tracker.db` and `raw.db` in the data dir.
  - Migrations: numbered per DB, tracked by `PRAGMA user_version`, one transaction each, run at
    startup.
  - `raw.db` sets `auto_vacuum=INCREMENTAL` before its first table.
  - Backups: `VACUUM INTO` of `tracker.db` before any pending migration and once a day, keeping 7.
    `raw.db` is not backed up.
  - Initial schemas:
    - `raw.db`: events, keyed by match GUID, sequence and timestamp.
    - `tracker.db`: settings (key/value); seasons, seeded with S22, S23 and S24; my IDs, including
      a pending-guess state; session break markers.
  - Retention job: runs 5 min after start, then every 24 h. Takes an injected `isRecording()`
    predicate (always false until WP3a wires it). Deletes in batches, then runs
    `incremental_vacuum`. Logs the event count and MB removed.
- **Tests** (each on a temp dir): migrations (fresh, upgrade, reinstall-finds-data); backup
  rotation; retention with an injected clock; a locked or unwritable file failure fired once for
  real.
- **Done when**: the Bun check is recorded (ADR), the tests pass, and starting twice on the same
  data dir migrates once and backs up as specified.

## WP3a: Recorder
Status: done (2026-10-19, `docs/plans/2026-10-19-wp3a-recorder.md`; ADR
`docs/decisions/2026-10-19-recorder-websocket-raw-store.md`). Notes for later WPs:
- `createRecorder` returns `isRecording()`, but `main.ts` doesn't hand it to anything yet: WP3b
  passes it to `scheduleMaintenance`.
- The connection status is waiting / connected / recording (`startStatsClient`'s `status()` and
  `onStatus`). "Stats API off" is left to WP3b's process detection.
- The hook gets `MatchSummary` plus check failures. WP4 adds stat handlers to `summary.ts`'s
  table and rows to `checks.ts`. `summary.facts` holds check inputs, not stats.
- `scripts/import-capture.ts` loads real captures into an empty data dir for WP4.
- **Map**: What the stream really sends; Raw event storage; Incomplete matches; New stats and MMR
  later (unknown-field logging); Background program form (reconnect, status states).
- **Depends on**: WP2.
- **Scope**:
  - Stats API client: WebSocket to `ws://127.0.0.1:49124` (revised 2026-10-19 from TCP: every
    capture used it and each frame holds exactly one envelope, so no framing parser is needed).
    `Data` is double-encoded. Reconnect every 5 s, backing
    off to 30 s. Connection state kept in memory for the header: waiting / connected / recording /
    Stats API off.
  - Raw persistence: every event except `UpdateState` stored in full; `UpdateState` downsampled to
    about 2/s; `Loadout[]` stored once per match; leading `PlaylistId: 0` states ignored.
  - Match lifecycle per `MatchGuid`: joined in progress (no `MatchInitialized`); exits signalled
    only by `MatchDestroyed`.
  - Wire WP2's `isRecording()` to the lifecycle.
  - A finished or orphaned match calls a "match finished" hook (a no-op until WP4).
  - Unknown event names and fields logged once per run.
  - Fixtures (see "Test fixtures") plus a replay tool: a fake Stats API server that streams a
    fixture or capture at real or fast speed.
- **Decision — orphaned matches**: after a game crash, PC sleep or tracker restart, a match never
  gets `MatchDestroyed`. Finalise it as left at startup, or after a timeout with no events. The
  WP3a plan picks the timeout.
- **Tests**: envelope parsing; downsampling rate; lifecycle per fixture
  (full match, left early, joined in progress, orphaned); unknown-field logging.
- **Done when**: replaying each fixture through the fake server stores the expected raw events and
  lifecycle calls.

## WP3b: Background process
Status: done, reviewed 2026-10-20 (`docs/plans/2026-10-19-wp3b-background-process.md`; ADR
`docs/decisions/2026-10-19-supervisor-autostart.md`). Notes for later WPs:
- WP5a builds its router on `startHost` (`src/server/host.ts`). It inherits the `Host` check, which
  allows only `127.0.0.1:<port>` and `localhost:<port>` against DNS rebinding. Everything except
  `POST /api/shutdown` is 404 today.
- The dashboard's status is `client.status()` plus the game watch's `statsApiOff()`: game
  running ≥ 60 s (on a 20 s poll) while still waiting. `statsConfig()` gives the latest Stats API
  config check (install dir, file in effect, values, `problems`), so the status can name the fix.
- The "no data" toast lands in the notification panel but **doesn't show over the full-screen
  game** (Windows suppresses banners). The dashboard status is the reliable signal. WP8 owns the
  toast switch and can try an urgent/priority toast.
- The background tracker is a compiled snapshot: code changes reach it only through
  `bun run install-autostart`, which `bun run deploy` wraps between `check` and `recompute`. `bun run dev` runs the source on port 49101 with `.dev-data/`.
- Exit codes: 0 stop, 2 start failed, 3 port taken; the supervisor restarts everything else too.
- **Map**: Background program form; Running (Q12).
- **Depends on**: WP3a.
- **Scope**:
  - Process host: bind the dashboard port before connecting to the game; if it's taken, log and
    exit.
  - Minimal HTTP server (`node:http` under Bun, or `Bun.serve`) with a shutdown endpoint that
    requires a custom header, plus `bun run stop`.
  - `bun run install-autostart` / `uninstall-autostart`: a Task Scheduler at-logon task for the
    current user, with restart on crash and no second instance.
- **Decision — the "no data within about 60 s" toast**. It needs:
  1. Detecting that the game is running while its port is closed, e.g. polling the process list
     for `RocketLeague.exe`. This also drives the "Stats API off" state.
  2. Raising a Windows toast with no native dependency, e.g. PowerShell
     `Windows.UI.Notifications`.

  Try both once for real.
- **Footprint (Q12)**: measure CPU and RAM idle and while recording a fast replay. Proposed pass
  threshold: **under 1% CPU and under 100 MB RSS while recording**; the WP plan confirms it with
  the user. Record the figures.
- **Tests**: second instance exits on the bound port; the shutdown endpoint rejects a request
  without the header; autostart install/uninstall run once for real.
- **Done when**: autostart starts the process at logon, it records a replay, `bun run stop` stops
  it, and the footprint figures are recorded against the threshold.
- **Milestone (after WP4a)**: the user installs autostart and plays normally, so real data builds
  up during the UI work. `recompute` makes early recording safe: it backfills WP4b's extras for
  matches still inside the 90-day raw retention.

## WP4: Match-record computation (split into WP4a core and WP4b extras)
WP4a status: done (2026-10-20, `docs/plans/2026-10-20-wp4a-match-records.md`; ADR
`docs/decisions/2026-10-20-match-records-per-player.md`). It covers the schema, the write path
(hook and `bun run recompute`), result, flags, MVP, identifying you, the playlist map, and the
scoreboard and statfeed counts. Changes from the scope below:
- Records cover every player and don't depend on `my_ids`; `teams_seen` (a bitmask) replaces
  "on your team at any point", and pages resolve "you" at read time (see WP5a).
- A match with no winner: leave, superseded or timeout is a loss; restart is unknown.
- Each player stat keeps its highest value over the states after `MatchEnded`, not the frozen
  snapshot; a no-contest `MatchEnded` (-1) has no winner.

WP4b status: done (2026-10-20, `docs/plans/2026-10-20-wp4b-match-extras.md`; ADR
`docs/decisions/2026-10-20-match-extras-play-view.md`). It covers the extras (seven
`match_players` columns from a registry) and one `match_goals` row per goal. Changes from the
scope below:
- Every stat reads one play view instead of `compute(events, summary)`, and the registry is
  player-scoped only. Crossbar hits became `woodwork_hits`, because posts fire it too. The
  fastest goal is `match_goals.speed_kmh`.
- The close / mid / long class is computed at read time by `goalRange` (`src/shared/goal-range.ts`)
  from the stored distance.
- For WP5a:
  - A pre-WP4b match and a 0–0 match both have no `match_goals` rows. Tell them apart by
    `match_players.woodwork_hits`, which is null only when the extras were not computed.
  - Car stats are null for players without car state (the other team). Aggregate supersonic
    and empty-boost shares as Σ ms ÷ Σ `car_ms`, and boost as a `car_ms`-weighted mean.
  - Own goals are `match_goals.own_goal`.
  - After the WP4b commit, `bun run recompute` backfills matches recorded before it.
- **Map**: Recap content; Incomplete matches; Inferred MVP; Identifying you; Playlist ID mapping;
  What the stream really sends; Recap layout (goal map, extras); New stats and MMR later.
- **Depends on**: WP3a (fixtures, hook), WP2 (migrations).
- **Scope**:
  - Migration: the match table, plus per-player rows per match: name and `PrimaryId`, team,
    scoreboard line, MVP (actual or inferred), whether they were on your team at any point.
  - Stat pattern: a registry of small pure functions, each computing one stat over one match's
    events. Adding a stat means a function plus a migration. The "match finished" hook can fire
    twice for one guid (a match reopened after Reconnect), so writing a record is an upsert.
    `bun run recompute` rebuilds records
    from `raw.db` for matches still inside retention.
  - Computations, all TDD'd on fixtures:
    - **Result**: from `MatchEnded`/`Win` when present; otherwise the decided-match rule (an
      overtime goal, or 0 s left with different scores); otherwise a left match counts as a loss.
      Keyed on `TeamNum`, using the scoreboard snapshot taken at `MatchEnded`.
    - **Flags**: left early, joined in progress, inferred result, inferred MVP.
    - **Inferred MVP**, where a tie means no MVP.
    - **Identifying you**: camera target plus the my-IDs list. An unseen ID becomes a pending
      guess, used until it's confirmed in WP8.
    - **Playlist mapping**: a data file mapping ID to name and group. An unknown ID is stored raw,
      shown as "Unknown playlist (id)" and logged.
    - **Your scoreboard and statfeed counts.**
    - **Extras**: hardest shot and fastest goal (km/h per the capture findings); crossbar hits;
      average boost, supersonic %, time on empty; aerial touches. Collapse consecutive duplicate
      `BallHit` events first (findings doc).
    - **Goal-map points**, one per goal, at the scoring team's last touch: location from
      `BallHit.Ball.Location`; deflected, aerial; speed, distance and height for the hover; a
      close / mid / long class; the scorer, for "your share" of the team's goals. Plus the
      own-goal count.
- **Done when**: each fixture match yields its expected record, and a live replay writes the same
  record as `recompute`.

## WP4c: Rule registry and recomputable raw data (split into WP4c-a registry and WP4c-b retention)
WP4c-a status: done, deployed (2026-10-20, `docs/plans/2026-10-20-wp4c-a-rule-registry.md`). It
covers the registry and its backfill, the generated `docs/definitions.md` and its sync test, the
rule-change flow, the per-match rule versions (a JSON map `{ruleId: version}` in
`matches.rule_versions`, the user's choice over one integer), and `bun run rules-diff` with its
test. Done when every current rule has an entry, the doc is in sync, and `rules-diff` reports no
change against the deployed DB.

WP4c-b status: done, deployed 2026-10-21 (`docs/plans/2026-10-20-wp4c-b-retention-split.md`,
ADR `docs/decisions/2026-10-20-raw-thinning.md`). It covers the retention split below, flagged
matches exempt and kept as the rule corpus, and the thinning tests and the 46-match check. Must
ship before mid-January 2027. The 46-match check: 45 thinned (6,572 of 42,974 states kept), 1
exempt, 1 lobby whole; raw.db 98.1 → 27.3 MB; rules-diff no change. Live after deploy: raw.db
migrated to 2, rules-diff over 13 matches no change.
Decisions already made (2026-10-20):
- **Thinning is change-only.** After 90 days, an `UpdateState` is dropped only when it changes
  nothing the scoreboard rules read: players' Name/PrimaryId/Shortcut/TeamNum and scoreboard
  stats, the teams' scores (or that the scoreboard is missing), PlaylistId, Arena, bOvertime, and
  a clock reading not already the running clock (from any event). The first and last states stay;
  kept states stay byte-for-byte. Measured on the live raw.db (13 matches): 1,807 of 13,080
  states kept, ~1,470 → ~247 KB per match.
- **Dense outputs are snapshotted in raw.db.** Thinning runs `readMatch` on the full raw first and
  stores what thinned raw can't support (the four car stats, the camera key) in a raw.db table;
  recompute of a thinned match substitutes them before the checks. Recompute and rules-diff keep
  needing only raw.db. Flag exemption is decided by that same `readMatch` (flagged under current
  rules → not thinned), so retention doesn't read tracker.db.
- Notes from WP4c-a's plan review: "changes nothing" compares with the previous *original* state,
  not the previous kept one; `Teams` absent vs incomplete are told apart; `rejectedScoreboards`
  and `cameraTargets` counts change under thinning but no flag can, since a positive count means
  the match is flagged and so not thinned.

The original scope, before the split:

- **Why** (grilled 2026-10-20, after WP4b): the stat rules are our own reading of the game's data:
  thresholds, attribution, goal and result rules, player identity. Their current form lives only
  in code. Their reasoning is spread over write-once ADRs, plan Review logs and this roadmap, so
  it goes stale as soon as a rule changes. Two WP4b rules are only in its Review log: the
  last-touch check compares only when both sides are known, and `resolveRef`'s attribution.
- **Depends on**: WP4b. It comes before WP5a for two reasons:
  - WP5a–WP7 add a dozen more rules: the session gap, the 4am cutoff, playlist groups, the 30-day
    baseline, remark thresholds.
  - The retention change must land before the first captured matches leave the 90-day window,
    in mid-January 2027.
- **Dev side** (not shipped in the app):
  - A rule registry in code. Each entry has an id, a one-line rule, its constants, the checks
    that guard it, the evidence it rests on, a version and its ADR. Every rule from WP3a–WP4b is
    backfilled.
  - `docs/definitions.md` is generated from the registry, and a test fails when it's out of date
    or names a check id that doesn't exist. It is the current source; plans, ADRs and reviews
    stay as dated history.
  - `bun run rules-diff` recomputes every stored match into a scratch DB under the working tree's
    rules. For each stat, it reports how many matches moved and by how much.
  - The rule-change flow:
    1. Edit the entry and bump its version.
    2. Read the diff.
    3. Write an ADR if the change passes the ADR gate.
    4. Run `bun run deploy`.
- **App side**:
  - **Retention split**. This revisits WP2's 90-day rule for all raw events.
    - Measured on the live `raw.db` (13 matches): `UpdateState` is 94% of the payload, and every
      other event together is about 85 KB per match.
    - Non-`UpdateState` events are kept indefinitely. After 90 days, `UpdateState` is thinned to
      what scoreboards need; the plan decides how.
    - Most rule changes can then reach every match. A recompute must never overwrite a stat that
      the thinned raw can no longer support, such as the car stats.
  - A per-match `rules_version`, so matches computed under older rules can be told apart. The end
    user may decline to recompute.
  - Flagged matches are exempt from retention. That keeps real oddities to fit rules to, and they
    become the rule corpus that `rules-diff` and the tests run on.
- **Tests**:
  - The registry and the doc stay in sync.
  - Thinning on a seeded raw DB: what's kept, what's thinned, and flagged matches left whole.
  - Recompute from thinned raw equals recompute from full raw for every rule that doesn't read
    dense `UpdateState`.
  - `rules-diff` across two rule versions reports the stat that moved.
- **Done when**:
  - every current rule has an entry, and the generated doc is in sync;
  - the 46 real captured matches recompute identically from thinned raw, except for the stats it
    can't support;
  - `rules-diff` reports no change against the deployed DB.

## WP5a: Query logic and API
Status: in progress, split a/b (2026-10-21; logic + API is ~1,400 lines, over one session).
- **WP5a-a** (done 2026-10-21; decision `docs/decisions/2026-10-21-query-sessions-baseline.md`):
  the pure query logic and the read layer over `tracker.db`, with their rule entries.
  Plan: `docs/plans/2026-10-21-wp5a-a-query-logic.md` (user decisions there: session key = first
  match's GUID; baseline = `[session start − 30 days, session start)`; offline playlists out of
  "everything"; LTMs under "Extra modes"; Official Tournament out of "All ranked").
- **WP5a-b** (done 2026-10-21; plan `docs/plans/2026-10-21-wp5a-b-api.md`, review
  `docs/reviews/2026-10-21-wp5a-b-api.md`). Handoff to WP5b: the endpoint table and response
  schemas are in the plan and `src/shared/schemas/`; the tracker serves `RLTRACKER_STATIC_DIR` or
  nothing, so WP5b settles the installed `dist` path; one SSE stream per tab hits the browser's 6
  connections per host, so share one across tabs. Original scope: router, static `dist` + `index.html` fallback, Zod schemas, endpoints, SSE, the
  "start new session" POST, contract tests. Decided so far:
  - The host starts before storage (`src/server/main.ts`), so it gains `mount(handler)`; `/api/*`
    answers 503 `{error:"starting"}` until mounted.
  - Writes other than shutdown require a custom header (`X-RLTracker-Request: 1`): the Host check
    stops DNS rebinding, not a cross-site form POST to 127.0.0.1. No CORS headers, so other sites
    can't read GET or SSE responses.
  - Response shapes as Zod schemas in `src/shared/schemas/`, so contract tests parse with them and
    the web gets inferred types.
  - SSE: `status` sent on change (client `onStatus` + a short poll for `statsApiOff`),
    `match_ended` {guid, sessionKey} after `writer.save` succeeds, a heartbeat comment.
  - Endpoints sketch: status, events, sessions (range + months), session detail, match
    detail, period aggregate, seasons, `POST` break. The b plan settles them.
  - `staticDir` is an option; the compiled tracker's real `dist` location is confirmed with WP5b.
  - From WP5a-a's review: validate at the boundary (Zod) what the query logic takes on trust: `day`
    as `YYYY-MM-DD` and a real date, `from`/`to` finite, the filter in its union, guids an array of
    strings. Seasons are validated where they are written.
  - Compose a page in one place, not per endpoint: cut sessions over every match
    (`readMatchTimes`), `currentSession` on that whole list, `sessionsPlayed` and `inFilter` for
    what's listed and aggregated, `baseline` over filtered rows. A wrong order gives plausible
    wrong numbers.
  - Per-request cost: read only the range a page shows, and compute a baseline only for the
    session being opened, not for every row of a list (each is a 30-day aggregate).

The original scope, before the split:
- **Map**: Session (Q8); Periods; Period views (playlist dropdown, comparisons); Recap layout
  (30-day baseline); Friends (private exclusion); Dashboard stack (server, SSE, Zod).
- **Depends on**: WP4a (WP4b only for the extras).
- **"You" and your result** (from WP4a): join `match_players.primary_id` with `my_ids` (not rejected) to
  find your row; "with you" is `me.teams_seen & p.teams_seen != 0`. Your result
  is `resultFor` in `src/shared/result.ts`, null meaning no W/L shown; a match with no "you" row
  (spectated) has no result. Playlist names come from `playlistInfo` in `src/shared/playlists.ts`,
  since records store the raw ID.
- **Decision — session identity**. Sessions are computed at query time, cut at the 30 min gap plus
  manual break markers, and not stored, so the later re-cut setting stays possible. A stable key is
  needed for the `/recap/:session/...` URLs, remark picks and their history, and placing break
  markers. Suggested key: the session's first match (GUID or start time). The WP plan settles it.
- **Scope**:
  - Pure, TDD'd logic:
    - Sessions.

## After v1
The map's "Later, not v1" items stay in the map; this roadmap doesn't copy them. These come from
the WP4c grilling (2026-10-20):
- **Evidence bands**, dev side. Each registry rule gets a metric for the data it rests on, such
  as hits per touch, the 50/50 share, car coverage or aerial-goal agreement. The metric carries
  the band measured when the rule was decided, and is recomputed over stored matches. Per-match
  checks catch broken data; these catch the basis of a rule shifting. They are folded into the
  checks framework as dataset-level checks, starting as a dev report.
- **End-user recalculation**, app side.
  - After an update that changes rules, the app lists what changed, in plain words generated from
    the registry.
  - It offers "Recalculate the last N days / all". Nothing changes automatically, and new matches
    use the new rules.
  - Pages note when a period mixes rule versions.
  - This belongs with the end-user install and update path, which v1 doesn't design.
