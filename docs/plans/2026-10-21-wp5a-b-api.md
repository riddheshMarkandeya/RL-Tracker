# WP5a-b: the dashboard API

## Context
WP5a-a shipped the pure query logic and the read layer (`src/shared/periods.ts`,
`src/shared/playlist-filter.ts`, `src/server/query/{sessions,aggregate,read}.ts`). The pages
(WP5b–WP7) still have nothing to call: the host (`src/server/host.ts`) answers only
`POST /api/shutdown` and 404s everything else. WP5a-b adds the HTTP layer: a router, static
`dist` with an `index.html` fallback, Zod schemas, the JSON endpoints, SSE, the "start new
session" POST, and contract tests against a seeded temp DB. Roadmap: `docs/plans/2026-10-16-v1-roadmap.md`
→ "WP5a: Query logic and API" → WP5a-b. Tier: Substantial (new module, several design calls).
Roadmap done-criteria: the contract tests pass, and SSE delivers "match ended" during a replay.

## Constraints that bind this plan
- Handoff decisions (roadmap WP5a-b list): `mount(handler)` with 503 `{error:"starting"}` until
  mounted; writes other than shutdown need `X-RLTracker-Request: 1`; no CORS headers; response
  shapes as Zod schemas in `src/shared/schemas/`; SSE `status` / `match_ended {guid, sessionKey}` /
  heartbeat; `staticDir` is an option; Zod-validate at the boundary what the query logic trusts
  (`day` a real `YYYY-MM-DD`, numbers finite, the filter in its union); compose each page in one
  place in the right order; read only the range a page shows, and compute a baseline only for the
  session being opened.
- Map, "Dashboard stack": a tiny router (Hono only if routing gets messy), React Router paths
  served `index.html` by the server, Zod types shared with the web. "Recap layout": picker = last 2
  weeks by day plus month folds (count and W–L) loaded lazily; "2nd of 2 that day"; dropdowns list
  only playlists present, no counts.
- Cross-cutting: loopback only; pages read match records, never `raw.db`; no fake zeros (the
  aggregates already return nulls); structured logger at decision points and failures.
- Project rule (unseen data shapes): flag and add a Watch item, don't invent handling.

## Approach

### 1. Host gains `mount` (`src/server/host.ts`)
- `Host.mount(handler: (req: Request, server: Server) => Response | Promise<Response>)`. The Host
  check and the shutdown route stay in the host, ahead of everything. Before mount, every other
  request gets 503 `{error:"starting"}` (JSON). A second `mount` throws (programming error).
- `server` is passed because Bun's HTTP idle timeout (default **10 s**, `bun-types/serve.d.ts:871-877`)
  would close a quiet SSE stream. `/api/events` calls `server.timeout(req, 0)`.
- Not `Bun.serve({routes})`: Bun matches those before `fetch`, so they would skip the Host check.

### 2. API module (`src/server/api/`, new)
- `router.ts`: a route table `{ method, path: "/api/sessions/:key", handler }`, matched on
  segments with `:param` captures. A literal segment beats a `:param` whatever the table order,
  so `/api/sessions/months` is never read as a key. Unknown `/api/*` → 404
  `{error:"not_found"}`; known path, wrong method → 405. About 30 lines; no dependency.
- `static.ts`: `serveStatic(staticDir, pathname)`. A file under `staticDir` is served via
  `Bun.file`; any other non-`/api` GET gets `index.html`. The path rules (Windows):
  - `decodeURIComponent` inside a try; a `URIError` → 404.
  - Reject a NUL byte.
  - `resolve(staticDir, "." + decoded)`, then reject it if `relative(staticDir, it)` starts with
    `..` or is absolute. This covers `%2f`/`%5c`, `/C:/…`, `\\server\…` and a sibling such as
    `dist-evil`.
  - A directory → the `index.html` fallback, not a file read.
  - `staticDir` null, or no `index.html` → 404 "dashboard not built". WP5b builds `dist`; main
    passes `RLTRACKER_STATIC_DIR` or null, and WP5b settles the installed default.
- Every API response carries `X-Content-Type-Options: nosniff`. There are no CORS headers.
- `events.ts`: the SSE hub. `subscribe()` returns a `ReadableStream` response
  (`text/event-stream`, `cache-control: no-store`). It sends the current `status` at once, then
  `status` on change, `match_ended`, `session_break`, and a `: hb` comment every 15 s.
  - It unsubscribes on `req.signal` abort or a stream cancel, and `stop()` closes every stream.
  - A cap of 16 subscribers: a no-cors fetch from any site passes the Host check and can hold a
    stream open, though it can't read it. Over the cap the oldest stream is ended (EventSource reconnects; it never does after a 503) and `api/sse_cap` (warn) is logged; revised in review round 1.
  - **Status changes come from one 1 s poll** of a `statusSnapshot()` (client status,
    `statsApiOff()`, config problems), sending only when it differs. This revisits the handoff's
    "client `onStatus` + a short poll": a poll alone covers both sources, and up to 1 s of lag on
    "recording" doesn't matter for a header badge.
- `pages.ts`: the page composition, the one place the order lives. It takes `QueryReader` and
  `now`, and does no HTTP. Each page begins with the same **index**:
  - `cutSessions(readMatchTimes(), readBreaks())` over every match.
  - `currentSession` on that whole list.
  - `readResults()` (§5), one light query: per match, the playlist, whether you played, and your
    result.
  - A session is assigned to `dayOf(session.startedAt)`. Its rows are always found **by its
    guids**, never by a `started_at` range: a session starting at 03:30 belongs to the day
    before, but its later matches fall after that day's end.

  The pages:
  - `sessionList(filter, fromDay, toDay)`: the played sessions (results + `inFilter`) whose day is
    in range, as summaries. "2nd of 2" is numbered over the sessions listed under the active
    filter, so a hidden session never makes "2nd of 3" with two shown. The number can change with
    the filter, which is intended.
  - `monthFolds(filter, beforeDay)`: per month before the day, the count of played sessions and
    W–L, all from the index. There is no full `readMyMatches`.
  - `currentSummary(filter)`: the current session's summary if it has a match under the filter;
    else null.
  - `sessionDetail(key, filter)`:
    - The session is found in the full cut; an unknown key → null → 404, for example a stale key
      after a break re-cut it.
    - `readMyMatches({guids})`, then filter, giving the matches list, `aggregate`, `byPlaylist`
      and `playlistsPresent` (from the unfiltered played rows).
    - The baseline: `readMyMatches({from: daysBefore(start, 30), to: start})`, filtered, then
      `baseline()`. A match-level window, as WP5a-a decided.
    - Goals for the goal map: `readGoals(filtered guids)`.
    - `prev`/`next`: the neighbouring played sessions under the filter, from the index. There is
      no walk.
    - `current` is a boolean.
  - `matchDetail(guid)`: the match, every player (scoreboard, `isMe`, MVP), its goals, check
    flags, your result and its session key.
  - `period(spec, filter)`:
    - `periodRange` (null → 404 for an unknown season).
    - `readMyMatches({from, to})`, then filter, giving `aggregate` and `playlistsPresent`.
    - `sessions`: the played sessions with at least one filtered match in the range, from the
      index. A session crossing the edge counts in both periods.
    - Buckets, the previous period and sparklines are WP7's.
  - `sessionKeyOf(guid)`: from the full cut; used by `match_ended` and `matchDetail`.
- `index.ts`: `createApi({ tracker, reader, status, staticDir, logger, now })` returns
  `{ handle, matchEnded(guid), stop() }`.
  - `handle`: write methods without the custom header → 403. Route `/api/*`, else serve static.
    Query params are parsed with the Zod param schemas (bad → 400 `{error:"bad_request", issues}`).
    Handler errors → 500 `{error:"internal"}` plus a log line.
  - `matchEnded(guid)`: computes `sessionKeyOf` and publishes. It is best-effort (broad catch,
    commented): it runs inside the recorder's hook, and a failure must not mark the save failed.

### 3. Endpoints
| Method | Path | Params | Returns |
|---|---|---|---|
| GET | `/api/status` | none | `{connection, statsApiOff, configProblems}` |
| GET | `/api/events` | none | SSE: `status`, `match_ended {guid, sessionKey}`, heartbeat |
| GET | `/api/sessions` | `filter`, `from`, `to` (days) | `{sessions: SessionSummary[], currentKey}` |
| GET | `/api/sessions/months` | `filter`, `before` (day) | `{months: {month, sessions, wins, losses}[]}` |
| GET | `/api/sessions/current` | `filter` | `{session: SessionSummary \| null}` (the header chip) |
| GET | `/api/sessions/:key` | `filter` | session detail (above) |
| GET | `/api/matches/:guid` | none | match detail (above) |
| GET | `/api/period` | `kind`, `day` \| `season`, `filter` | period view (above) |
| GET | `/api/seasons` | none | `{seasons: Season[]}` |
| POST | `/api/sessions/break` | header only | `{at}`, after `INSERT OR IGNORE INTO session_breaks` at `now()`; publishes SSE `session_break {at}` so other tabs refetch |

- `SessionSummary`: `{key, day, ordinal, ofDay, startedAt, endedAt, matches, wins, losses,
  results: ("win"|"loss"|null)[]}`. The web caps the strip at 24.
- `filter` on the wire: `everything | ranked | casual | extra | private | <playlist id>`, parsed
  into `PlaylistFilter`. The default is `everything`, and each page passes its own default.

### 4. Schemas (`src/shared/schemas/`, new)
- `params.ts`:
  - `filterParam`.
  - `dayParam`: `z.iso.date()`, which already rejects `2026-02-30` and Feb 29 in non-leap years.
    It also needs a year of 1000 or later: `Date.UTC` and `new Date(y, …)` map years 0–99 onto
    1900–1999 (`periods.ts:36,57`).
  - The `from <= to` check on the sessions params.
  - `periodParams`: a discriminated union on `kind` matching `PeriodSpec`.
  - The `sessions`, `months` and `current` param objects.
- `responses.ts`: the `Aggregate`, `SessionSummary`, `SessionDetail`, `MatchDetail`, `Period`,
  `Status`, `Seasons` and SSE event schemas. The server code is typed by `z.infer` of these, so a
  shape drift is a type error. The contract tests also `parse` real responses with them.
- `MyMatch` is reshaped to the wire type only where it needs to be. `aggregate.ts`'s `Aggregate`
  interface is kept, with a compile-time check that it matches the schema's inferred type
  (`satisfies`/assignability both ways), so the two can't drift.

### 5. Read-layer additions (`src/server/query/read.ts`)
- `MyMatch.flagged` (from `check_flags != '[]'`), for the amber dot, and
  `MyMatch.scoreTeam0/scoreTeam1`, for the match cards and the numbers table.
- `readResults()`: one query, no statfeed or goals:
  - Per match: `guid, startedAt, playlistId, played, result`.
  - "You" use the same `MINE` join and `pickMe` rule, so a match with two of your ids still gives
    one row.
  - `result` comes from `resultFor`.
  - Its `query/read` ms is logged like the others.
- `readGoals(guids)`: every goal of those matches with position, team, scorer/assister/toucher,
  distance, speed, deflected, aerial and own goal. The web classifies range with `goalRange`.
- `readMatch(guid)`: the match row and every player row, with `isMe` resolved with the same
  `MINE` predicate and `pickMe` rule.

### 6. Wiring (`src/server/main.ts`)
- Create the reader after `openStorage`.
- `let api: Api | undefined` is declared **before** `createRecorder`. The recorder's
  `onMatchFinished` runs `writer.save(...)` and then `api?.matchEnded(guid)`. Startup recovery
  fires before the API exists, so the call is skipped; a `const` declared later would instead
  throw a TDZ error, logged as a misleading `hook_failed`.
- After `startGameWatch`: `createApi(...)`, then `host.mount(api.handle)`.
- `api.stop()` is added to `stop()`'s steps, before `host`.

### Logging (what each line answers)
- `api/request` (info): method, route pattern (not the raw path), status, ms. Which endpoint is
  slow or failing? Static files are logged only on 404.
- `api/bad_request` (warn): route and Zod issue paths. What did the web send wrong?
- `api/failed` (error): route, err. What threw?
- `api/write_rejected` (warn): method, path, origin. Was there a cross-site write attempt?
- `api/sse_open` / `api/sse_close` (info): subscriber count. Do streams leak?
- `api/sse_cap` (warn): is something holding streams open?
- `api/session_break` (info): at. When did the user cut a session?
- `api/match_ended` (info): guid, sessionKey, subscribers; `api/match_ended_failed` (error).
  Did the push go out after a save?
- The existing `query/read` lines give per-read ms under each request.

## Implementation notes
- `period()`: each match counts in the period it started in; a session crossing an edge counts in
  both periods' session counts. The day list and month folds count a session whole on its first
  match's day. (The Approach bullet was followed where step 6's wording was ambiguous.)
- `readMatchTimes` and `sessionsPlayed` were removed: `readResults` carries the times, and the
  pages index owns the "played under the filter" rule.
- `main.ts` uses `parts.api?.matchEnded(...)` (declared before the recorder) instead of a separate
  `let api`; the same TDZ safety.
- Bun's 10 s idle timeout was measured closing a silent stream at about 12 s, so the stream test
  waits 14 s; without `server.timeout(req, 0)` it fails with ECONNRESET.
