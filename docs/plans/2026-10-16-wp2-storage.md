## Design
### Layout
- `src/server/db/sqlite.ts` is the thin driver seam:
  - `openDb(path, { busyTimeoutMs?, autoVacuum? })` returns a `Db` with `run`, `get<T>`,
    `all<T>`, `transaction(fn)`, `pragma` and `close`.
  - `transaction` wraps bun:sqlite's own `db.transaction(fn).immediate()`. `fn` is typed as
    synchronous: an async callback would commit before its awaits run.
  - It is the only file that imports `bun:sqlite`.
  - On open it sets `busy_timeout` (default 5000), then `auto_vacuum` when asked (only takes
    effect on a new file), then `journal_mode=WAL` and `foreign_keys=ON`. `auto_vacuum` must come
    before WAL: switching to WAL writes page 1, and that fixes the vacuum mode. If SQLite answers
    with a mode other than `wal` (a filesystem without WAL support), `openDb` throws.
  - `openStorage` creates the data dir (`mkdirSync`, recursive). A filesystem error there is
    also logged as `db/open_failed` and rethrown.
- `src/server/db/migrate.ts` — `migrate(db, name, migrations, { beforeMigrate?, logger })`.
- `src/server/db/migrations.ts` — `trackerMigrations`, `rawMigrations`: arrays of SQL strings;
  index + 1 = version.
- `src/server/db/backup.ts` — `backupTracker`, `pruneBackups`, `dailyBackupDue`.
- `src/server/db/retention.ts` — `runRetention`.
- `src/server/maintenance.ts` — `scheduleMaintenance` (moved out of `db/` in review: it needs
  `Storage`, which lives a layer up).
- `src/server/storage.ts` — `openStorage({ dir, logger?, now? })` → `{ tracker, raw, close }`.
- `main.ts` — opens storage, logs, closes, exits (WP3b makes it the long-running host).
Fixed operational values (keep 7 backups, 5-min first delay, 24 h interval, hourly backup
check, batch size, vacuum step) are
module constants, not `constants.ts`: they aren't planned user settings.

### Migrations
- Version = `PRAGMA user_version`. Each pending migration runs in its own `BEGIN IMMEDIATE`
  transaction; inside it, re-read `user_version` (a second instance that waited on the lock sees
  the work done and skips), run the SQL, set `user_version = N`, commit. A throw rolls back.
- DB newer than the code (`user_version` > known count) → log `db/newer_than_code` and throw:
  old code must not write a newer schema.
- `raw.db` is opened with `autoVacuum: "incremental"` (see `openDb`). The step-4 test asserts
  that it reads back as 2.
- The pre-migration backup (`beforeMigrate`) runs outside the migration lock, so two instances
  starting at the same moment could both back up. That costs one extra file, and WP3b's port
  bind stops a second instance anyway. Accepted.
- Timestamps are UTC epoch ms (`INTEGER`); season starts are local calendar dates (`TEXT`
  `YYYY-MM-DD`), per the map's Periods.

### Initial schemas
- `raw.db` v1: `events(id INTEGER PRIMARY KEY, match_guid TEXT NOT NULL, seq INTEGER NOT NULL,
  ts INTEGER NOT NULL, name TEXT NOT NULL, data TEXT NOT NULL /* JSON */, UNIQUE(match_guid,
  seq))`, index on `ts`. Downsampling and the once-per-match `Loadout` are WP3a's.
- `tracker.db` v1:
  - `settings(key TEXT PRIMARY KEY, value TEXT NOT NULL /* JSON */)`. No keys or Zod schema yet:
    WP8 defines both (`src/shared/schemas` is created then; roadmap note updated).
  - `seasons(id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE, start_date TEXT NOT NULL
    UNIQUE)` (a stable id because WP8 edits both name and date), seeded S22
    2026-03-11, S23 2026-06-09, S24 2026-09-23.
  - `my_ids(primary_id TEXT PRIMARY KEY, name TEXT, status TEXT NOT NULL CHECK (status IN
    ('confirmed','pending','rejected')), added_at INTEGER NOT NULL)`. `pending` = a guess waiting
    for "That's me"/"Not me"; `rejected` keeps "Not me" from being asked again.
  - `session_breaks(at INTEGER PRIMARY KEY)` — the manual "start new session" markers.

### Backups (`tracker.db` only)
- Into `<dataDir>/backups/tracker-<UTC yyyyMMdd-HHmmss-SSS>-<reason>.db` via `VACUUM INTO`;
  names sort chronologically. Reasons: `premigration`, `daily`. Written as `<name>.partial`
  then renamed, so a copy cut short never passes for a backup. A failure removes the partial;
  pruning removes any a killed process left.
- Pre-migration: when migrations are pending and `user_version` > 0 (a fresh DB has nothing to
  protect). A failed pre-migration backup aborts startup (logged): migrating unprotected is
  what the backup exists to prevent.
- Daily: at startup when the newest backup (any reason) is older than 24 h, when none exists, or
  when the newest is dated in the future (the clock moved back). Then checked hourly by the
  maintenance timer while no match is recording, so backups stay about 24 h apart without
  blocking a match. The file is stamped with the instant the check used. A failure is logged and
  startup continues.
- Prune after each backup: keep the newest 7 `tracker-*.db`; a delete failure is logged, not
  thrown.

### Retention (`raw.db`)
- `runRetention(raw, { now, isRecording, stopping?, logger })`: cutoff = now − `RETENTION_DAYS`.
  Skip if `isRecording()` at the start. Loop: `DELETE FROM events WHERE id IN (SELECT id FROM
  events WHERE ts < ? LIMIT 5000)`, yield to the event loop, then stop if a match started
  recording or `stopping()` (shutdown) is true. Then `PRAGMA incremental_vacuum(4096)` in steps
  with the same yield and checks, until the freelist is empty or a step frees nothing; a stopped
  run leaves the rest to the next. MB removed = (page_count before − after) × page_size.
- Deleting by event `ts` can cut the oldest match in two at the edge. Accepted: only a backfill
  of a match 90 days old would see a partial match, and backfill (later) only targets matches
  inside the window.
- Batches yield to the event loop through an injected `yieldFn` (default `setImmediate`), so the
  fake-timer tests don't hang.
- `scheduleMaintenance({ storage, isRecording = () => false, now, logger, yieldFn })` (global
  timers; the tests use `vi.useFakeTimers`) runs retention at +5 min and then every 24 h. A run
  that is skipped or stopped because a match is recording retries after 15 min, so a fixed play
  time can't starve it. The daily-backup check runs hourly, skipped while recording. It returns `stop()`, a promise that
  waits for a run in progress to stop; call it before closing storage. A failing run is caught and
  logged and the schedule continues (broad catch, commented: a maintenance error must never kill
  the recorder). **Wired into the process by WP3b** (main.ts still exits right away in WP2);
  roadmap note updated.

### Logging (cat `db` / `backup` / `retention`)
Questions the lines answer: Did startup open and migrate each DB, from which version to which,
how long? Was a backup made, why, how big, and what was pruned? Did retention run or skip, what
did it remove (events, MB), how long? What failed, on which file, with which SQLite code?
Events: `db/opened`, `db/open_failed`, `db/migrated` {db, from, to, ms}, `db/migration_failed`,
`db/newer_than_code`, `backup/created` {reason, path, bytes, ms}, `backup/failed`,
`backup/pruned` {removed}, `backup/prune_failed`, `retention/skipped_recording`,
`retention/stopped` {reason: recording | shutdown, events, batches},
`retention/done` {events, mb, batches, ms}, `retention/failed`; also `app/started`,
`app/stopped`, `app/start_failed` in `main.ts`. Logger is injected (default
`log`) so tests capture lines instead of writing to `%LOCALAPPDATA%`.
